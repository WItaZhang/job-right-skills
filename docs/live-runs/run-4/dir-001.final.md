# 大规模系统基础设施 · Senior/Staff IC

在新加坡/深圳/杭州这类年轻科技城市，做需要解决真正大规模（海量流量、PB 级数据）性能与可靠性挑战的基础设施工作，职级为 senior 或以上、以实际职责范围而非 title 判断，继续做 IC。

## 追问链

### I-001
- 时间：00:46
- 用户原话：我做了六年基础设施开发，想换一家做大规模系统的公司，最好在新加坡或深圳。
- 访谈者问题：（开场）
- 结论：开启两条追问链：(1) "大规模系统"背后的属性；(2) 新加坡/深圳共同的属性。另记录事实：6 年基础设施开发经验，需在后续确认 target level。

### I-002
- 时间：00:52
- 用户原话：规模大才有真正的性能和可靠性问题可以解，小系统的问题我都见过了。
- 访谈者问题："大规模系统"这件事，能给你带来什么？如果换到一家其他条件都合适、但系统规模不算特别大的公司，你会觉得少了什么？
- 结论：why 步骤完成。属性初步命名为"系统规模带来的、他还没见过的性能/可靠性技术挑战"，而非公司名气或规模本身。待 alt_test 确认：是公司规模还是系统/负载规模。

### I-003
- 时间：00:52
- 用户原话：新加坡或深圳是因为我想在一个年轻、科技公司密集的城市，周末有技术活动那种。
- 访谈者问题：（用户主动补充，未被追问）
- 结论：attribute 步骤完成（用户主动给出）。属性命名为"年轻、科技公司密集、有周末技术活动氛围的城市"，observable_criteria：科技公司密度、同龄从业者多、周末有 meetup/技术活动。待 alt_test 确认新加坡/深圳是否可替换为其他同属性城市。

### I-004
- 时间：00:58
- 用户原话：算。我要的是系统本身的规模，公司多少人无所谓。
- 访谈者问题：如果一家公司整体不算特别大（比如员工不到1000人），但它的核心基础设施要扛住海量流量或数据（比如服务数亿用户、或PB级数据处理），这种算你说的"大规模系统"吗？还是说公司本身的规模也是硬指标？
- 结论：alt_test 通过。属性确认为"系统/负载本身的规模"，公司人数不是条件。字段命名为 role.system_scale（而非 company.size）。

### I-005
- 时间：01:02
- 用户原话：会拒绝。我这次换工作就是为了这个，中等规模的我现在就在做。
- 访谈者问题：如果一个岗位其他条件都很合适，但系统规模只是中等（不是海量流量/PB级那种），你会因此直接拒绝吗？
- 结论：strength 步骤完成。role.system_scale 确认为 kind: hard, status: confirmed。

### I-006
- 时间：01:06
- 用户原话：杭州可以。柏林、西雅图理论上也行，但签证太麻烦，我不会主动考虑，不是绝对不行。
- 访谈者问题：如果是同样年轻、科技公司密集、周末有技术活动氛围的城市，但不是新加坡或深圳——比如柏林、西雅图，或者杭州——这些你会考虑吗？还是新加坡/深圳本身有别的原因（比如离家近、语言、签证之类）？
- 结论：alt_test 通过。属性确认为"年轻科技氛围"而非特定国家/城市；杭州确认符合。同时浮现出新的、独立的软条件：签证/办理难度会降低优先级但不是硬性排除（柏林、西雅图"理论上也行"但不会主动考虑）。记为 location.relocation_ease，kind 待定但用户已说"不是绝对不行"，倾向 soft。

- 结论：strength 步骤完成。location.city_profile 确认为 kind: soft, status: confirmed（加分项，非硬条件）。

### I-008

- 访谈者问题：（进度回顾，请用户确认/修正）
- 结论：用户确认回顾无误，并主动补充三项：(1) role.level：至少 senior，staff 更好，明确排除 mid（"我不看"=strength 已确认为 hard）；(2) role.nature：倾向 IC，strength 尚未测试，暂记 pending；(3) compensation.base：新加坡 SGD 200,000/年 base 为底线，深圳/杭州按购买力平价换算，"底线"一词 + 具体数字视为 hard 的直接确认。role.level 待做 alt_test（title vs 实际职责范围）以确认观察标准，用于后续列入 key_fields。

### I-009
- 时间：01:20
- 用户原话：看实际职责范围，title不重要。我要排除的是那种明确写给两三年经验、按ticket干活的岗位。
- 访谈者问题：职级这件事，如果一个岗位title写的是Senior，但实际职责已经接近staff（比如独立负责一个大系统的架构决策），你会因为title不是Staff就不考虑吗？反过来，title写Staff但实际内容更偏senior，你会觉得不够格吗？——你更看title还是实际的职责范围？
- 结论：alt_test 通过。role.level 的判断依据是实际职责范围/决策权，非 title 文字。observable_criteria 补充：独立负责大系统架构决策（正面）；面向 2-3 年经验、按 ticket 干活（排除）。role.level 满足 key_fields 条件（hard/confirmed + alt_test_ref + hard_confirmation_ref），加入 key_fields。

### I-010
- 时间：01:26
- 用户原话：带一两个初级的可以接受，不做绩效和招聘就行。正式的管理岗我会拒绝。其他维度今天不聊了，请整理方向，能确认就确认。
- 访谈者问题：如果一个岗位主要还是写代码、做架构，但带一点点管理成分（比如带1-2个初级工程师），你会因为这点管理成分而拒绝吗，还是可以接受？
- 结论：strength 步骤完成。role.nature 确认为 kind: hard, status: confirmed（可以少量 mentoring，但拒绝正式管理岗/绩效考核/招聘职责）。用户要求结束本次访谈，整理并在满足条件时确认方向。

### I-011
- 时间：01:32
- 用户原话：1 对，mid-level直接拒绝。2 不一定，如果系统特别对，base低一些可以谈，薪酬不是底线。
- 访谈者问题：最后两个确认：1. 职级：如果一个岗位其他条件都合适，但明确是mid-level（不到senior），你会直接拒绝，对吗？2. 薪酬：如果base低于这个数（新加坡SGD 20万/年，深圳/杭州按购买力折算），哪怕其他条件都合适，你也会拒绝，对吗？
- 结论：(1) role.level 的 strength 在独立追问中再次确认为 hard，hard_confirmation_ref 改为本条（不再借用 I-008）。(2) compensation.base 的 strength 测试结果与最初判断相反：用户明确表示"薪酬不是底线"，系统匹配得好时 base 可以低于该数字。compensation.base 由 hard 修正为 soft，status 仍为 confirmed（该数字是参考锚点/目标而非硬性下限）。
