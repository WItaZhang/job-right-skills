# Preference profile 与冲突澄清：研究结论

日期：2026-09-22。以下是拟议字段与人工验收例子，**尚未实现 schema 或访谈 skill**。
主要依据：[Job Search](../projects/job-search.md)、[JSON Resume](../projects/jsonresume.md)、[career-ops](../projects/career-ops.md)、[job-scout](../projects/job-scout.md)；交互参考 [example-critiquing](../primary/preference-elicitation.md)。

## 先分开事实、意图和限制

| 对象 | 记录什么 | 不能推断什么 |
|---|---|---|
| background_facts | 用户提供的经历、技能证据与来源 | 做过的岗位不自动成为未来目标 |
| goals | 兴趣、人生方向、想增加或减少的日常工作 | GitHub 项目名称不等于人生方向 |
| preferences | 明确表达的工作条件和优先程度 | “喜欢”不自动升级为 hard |
| constraints | 用户确认不可退让、且可验证的条件 | 未提及不等于没有限制 |
| open_questions | 尚未回答、含糊或冲突的问题 | 模型猜测不能填入 confirmed |

## 访谈维度

| 维度 | 需要澄清的问题类型 | 可观察的表达方向 |
|---|---|---|
| 兴趣与动力 | 哪类问题让你愿意持续投入，哪些工作想减少 | 产品领域、工作内容、想保留的技能 |
| 人生方向 | 这次换工作希望改变什么，时间跨度是什么 | 学习、稳定、影响力、生活安排的优先关系 |
| 压力承受 | 什么压力可接受，哪些模式不可持续 | 工时、值班、出差、模糊职责、截止期频率 |
| 风险容忍 | 哪些不确定性可接受，范围是什么 | 公司阶段、现金与股权比例、合同稳定性 |
| 角色与成长 | IC/管理、职责、成长方式 | 实际任务、导师支持、决策范围 |
| 地点与时间 | 远程/混合/现场、可工作地区、时区重叠 | 条件与适用日期、搬迁是否可协商 |
| 薪酬与身份条件 | 哪些是底线、口径是什么 | 币种、期间、base/total；身份条件只记用户陈述 |
| 团队环境 | 怎样的协作方式适合自己 | 会议、异步沟通、反馈、团队规模的偏好 |

问题用于未来访谈，本轮没有替用户填写答案。允许“无偏好”“跳过”“暂不知道”。这三种回答不能互换。

## 一条 preference 的最小信息

| 字段 | 研究建议 |
|---|---|
| id / profile_revision | 稳定编号与档案版本，使理由可追溯 |
| dimension / value | 维度和具体值；未知 value=null，不用 0/false 代替 |
| kind | hard / soft / unspecified；必须由用户确认强度 |
| priority / rationale | 软偏好的相对优先程度及原因，初期不强迫填写权重 |
| scope | 适用角色、地点、时间与例外，避免把局部条件泛化 |
| unit / basis | 金额、币种、期间、base/total 或时间单位；无法比较则待澄清 |
| status | confirmed / unknown / conflict |
| source_ref / stated_at / confirmed_at | 用户原话的私有引用、表达时间、确认时间；时间带时区 |
| conflicts_with / resolution | 冲突项编号、尚未解决的问题和最终决定 |
| supersedes / change_reason | 修订关联和原因，不覆盖旧版记录 |

真实原话和个人 profile 默认只在私有位置保存，公开仓库仅放合成例子。来源引用可以是私有访谈记录的编号，无需公开用户信息。

## hard、soft、unknown 的不同作用

1. **hard 已确认且岗位明确违反：**fail，展示约束及证据；软优势不能抵消。
2. **hard 已确认但岗位证据缺失/冲突：**unknown，进入待核实队列，不计作通过或明确拒绝。
3. **hard 已确认且证据满足：**pass；只在全部必需硬条件通过后比较软偏好。
4. **偏好本身未确认或互相冲突：**先澄清用户意图；不要依靠研究更多岗位替用户决定底线。
5. **soft：**展示满足、取舍、未知；缺失信息不当作零分，“无偏好”不参与比较。

判断结果使用 rejected / needs_clarification / needs_verification / eligible_for_comparison。
若已证实任一 hard 失败，可给 rejected 并同时展示其他未解决项；否则先处理偏好冲突，再处理岗位证据缺口。eligible_for_comparison 只代表可以比较，不是投递决定。

## 冲突澄清流程

发现两条要求不一致时，保留双方原话与 scope → 区分硬冲突、软取舍、时间/地点范围差异 → 问一个能改变判断的最小问题 → 记录用户回答 → 形成新 revision → 标记受影响的旧匹配结论待复核。

只有两个 hard 在同一适用范围内不可同时满足时，才是阻塞冲突；“喜欢创业环境但偏好稳定”可能只是软取舍，不能擅自判用户自相矛盾。两次表达不同也不自动认为最新一句覆盖旧值，除非用户明确说明修改。

可用中性 synthetic 情境帮助澄清；必须让用户有“都不要/尚不清楚”出口。跳过问题保持 unknown，不自动降级硬条件或替换答案。

## 人工验收例子（synthetic；尚未自动化）

| 输入 | 预期研究结果 |
|---|---|
| “只接受完全远程”与“必须每周现场三天”，同一角色和时间 | conflict，询问哪条应修改；不静默覆盖 |
| “目前必须远程，搬家后可混合” | 不直接判冲突；补齐生效时间与地点 scope |
| 用户要求远程，JD 未写工作方式 | needs_verification，remote=unknown |
| JD 明确全现场，用户已确认 remote 为 hard | rejected，即使薪酬或领域很吸引也不能抵消 |
| 两个薪酬数值分别为年 base 与月 total | 口径待澄清，不能直接比较 |
| 用户曾带团队，却没有说明未来偏好 | 管理经历是事实；IC/管理偏好保持 unknown |
| 用户说“对公司规模无偏好” | confirmed + any；不是缺失，不参与排名 |
| 想创业又重视稳定，均为 soft | 展示取舍，请用户进一步说明风险范围 |

验收重点是可追溯与正确保留未知，而不是填满档案或产生精确分数。
